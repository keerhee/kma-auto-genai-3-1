# 옵시디언 세컨드 브레인 — 개념 정리와 직무별 실습예제

> [!summary] 한 줄 결론
> 업무 원본 자료를 `raw/` 폴더에 넣고, Claude가 그것을 `wiki/` 폴더의 마크다운 페이지로 정리하게 하면, 새 대화를 열 때마다 자기소개와 자료 첨부를 반복하지 않아도 된다. 옵시디언은 그 폴더를 사람이 읽고 점검하는 창이다.

---

## 1. 왜 필요한가 — 기존 방법의 한계

AI와 새 대화를 시작하면 AI는 매번 나를 처음 보는 사람처럼 대한다. 지금까지 쓰던 해결책에는 각각 한계가 있다.

| 기존 방법 | 한계 |
|---|---|
| 프로젝트 지침(instructions) | 명함 한 장 분량이라 세부 자료를 담기 어렵고, 업무가 바뀔 때마다 사람이 직접 고쳐야 한다. |
| 메모리(memory) 기능 | 필요할 때 자동으로 꺼내 쓴다는 보장이 없어, "저장한 내용을 꺼내 써 달라"고 매번 말해야 한다. |
| 노션 같은 외부 DB | 매번 불러오고 읽고 해석하는 과정이 반복되어 느리고, 그때마다 크레딧(토큰)이 소모된다. |
| 매번 AI에게 원본 정리를 맡김 | 같은 정리를 대화마다 다시 하므로 역시 크레딧이 반복해서 낭비된다. |

**필요한 것**은 메모 한 장을 건네는 방식이 아니라, 내 머릿속을 복제해 언제든 꺼내 쓸 수 있는 두 번째 두뇌다.

## 2. 핵심 개념 — 냉장고 비유

| 비유 | 실제 구성 | 설명 |
|---|---|---|
| 마트에서 본 장(식재료) | `raw/` 폴더의 원본 자료 | 회의록, 엑셀, 메일, 보고서, 웹 수집 자료를 손대지 않은 상태로 둔다. |
| 손질된 재료 | `wiki/` 폴더의 마크다운 페이지 | 원본을 주제별로 요약하고 서로 링크로 연결한 정리본이다. |
| 냉장고 | 옵시디언 볼트(vault) | 정리본을 보관하고, 사람이 읽고 점검하며, 그래프로 연결 관계를 본다. |
| 요리사 | Claude(데스크톱 앱의 폴더 연결 또는 Claude Code) | 손질된 재료를 꺼내 주문(업무 요청)에 맞는 결과물을 즉시 만든다. |
| 주방 규칙 | `CLAUDE.md` 같은 규칙 파일 | 재료를 어떻게 손질하고 어디에 넣을지 정한 운영 규칙이다. |

> [!note] 출처 바로잡기
> 영상은 "세컨드 브레인을 카파시가 정립했다"고 소개하지만, **세컨드 브레인(Building a Second Brain)이라는 용어와 PARA 분류법은 티아고 포르테(Tiago Forte)가 대중화**한 개념이다. 안드레 카파시(Andrej Karpathy)가 제안한 것은 이 아이디어를 LLM에 맞게 바꾼 **"LLM Wiki" 패턴**이다. 원본(raw)은 그대로 두고, LLM이 위키(wiki)를 쓰고 유지하며, 규칙 파일(schema)이 그 방식을 정한다. 영상의 실습 구조(`raw → wiki`)는 바로 이 LLM Wiki 패턴이다.

### 2.1 세 층 구조

```text
MorningLiving_SecondBrain/        ← 옵시디언 볼트 = Claude가 연결된 폴더
├── CLAUDE.md                     ← 주방 규칙: 폴더 구조, 페이지 양식, 링크 규칙
├── raw/                          ← 원본(불변). 사람이 넣고 AI는 읽기만 한다
│   ├── 2026-10-20_주간회의록.md
│   ├── 거래처_리스트.xlsx
│   └── web/2026-10-25_핸드워시_경쟁사/   ← AI가 웹에서 수집한 자료
└── wiki/                         ← 정리본. AI가 쓰고 고친다
    ├── index.md                  ← 전체 목차
    ├── 00_나와 직무.md
    ├── 01_회사 개요.md
    ├── 02_용어와 상태 구분.md
    ├── 거래처/
    ├── 업무 프로세스/
    ├── 결정 기록/
    └── log.md                    ← 언제 무엇을 반영했는지 남기는 작업 일지
```

### 2.2 세 가지 기본 동작

| 동작 | 언제 쓰나 | 예시 프롬프트 |
|---|---|---|
| **인제스트(ingest)** | 새 원본을 `raw/`에 넣었을 때 | "raw 폴더에 새 파일을 넣었어. 인제스트해 줘." |
| **질의(query)** | 업무 결과물이 필요할 때 | "위키를 근거로 팀장님께 보낼 주간 보고를 써 줘." |
| **점검(lint)** | 주기적으로 위키 품질을 확인할 때 | "위키에서 서로 모순되거나 오래된 내용, 링크가 끊긴 페이지를 찾아 줘." |

### 2.3 위키에는 무엇이 보관되나 — 요약본이 아니라 정리본

위키는 원본 하나당 요약 하나를 만들어 두는 곳이 아니다. 여러 원본을 **주제별로 합쳐 다시 쓴 정리본**을 보관한다. 예를 들어 "거래처 A" 페이지는 거래처 리스트, 회의록 세 건, 변경 공지에서 거래처 A에 관한 내용만 모아 하나로 정리한 것이다.

| 구분 | 들어가는 것 | 성격 |
|---|---|---|
| `raw/` 원본 | 회의록, 엑셀, 메일, 웹 수집 원문 | 원본. 손대지 않는다 |
| `wiki/` 정리본 | 주제별 정리본, 결정 기록과 변경 이력, 페이지 사이의 링크 | 원본을 가공한 지식 |
| `wiki/` 산출물 | 주간 보고, 기획 초안처럼 Claude와 함께 만든 산출물 | 원본이 따로 없는 새 결과물 |

- 정리본의 사실마다 **근거 원본 파일명**이 붙어 있다. 세부 내용이 필요하면 Claude가 그 링크를 따라 `raw/`의 원문을 다시 읽는다.
- 그래서 위키는 가볍게 유지하고, 정확한 숫자와 원문 표현은 언제든 `raw/`에서 확인할 수 있다.

## 3. PARA와 결합하기

### 3.1 두 축은 겹치지 않는다

| 축 | 나누는 기준 | 질문 |
|---|---|---|
| `raw → wiki` | 가공 단계 | 손질 전 재료인가, 손질된 재료인가? |
| PARA | 실행 가능성 | 지금 실행 중인 일인가, 계속 맡는 책임인가, 참고 지식인가, 끝난 일인가? |

PARA(Projects · Areas · Resources · Archives)는 티아고 포르테가 제안한 분류법이다. 두 축이 다르기 때문에 **`raw/`는 그대로 두고 `wiki/` 안을 PARA로 나누면** 둘을 함께 쓸 수 있다.

```text
MorningLiving_SecondBrain/
├── CLAUDE.md
├── raw/                    ← 원본은 PARA로 나누지 않고 날짜·출처 단위로 쌓는다
└── wiki/
    ├── index.md
    ├── log.md
    ├── 1_Projects/         ← 기한과 목표가 있는 일
    ├── 2_Areas/            ← 끝나지 않고 계속 맡는 책임
    ├── 3_Resources/        ← 참고 지식
    └── 4_Archives/         ← 끝났거나 더 이상 쓰지 않는 것
```

> [!important] PARA 칸 안에도 정리본이 들어간다
> `wiki/` 아래 PARA 네 칸에는 모두 정리본과 산출물이 들어간다. 원본은 어느 칸에도 옮기지 않는다. 원본을 옮기면 위키에 적어 둔 출처 경로가 깨지기 때문이다.

### 3.2 원본(raw)은 왜 PARA로 나누지 않나

**원본 하나가 여러 칸에 걸친다.** 주간회의록 한 건에는 11월 프로모션(Projects), 거래처 관리(Areas), 용어 정의(Resources)에 관한 내용이 함께 들어 있다. 원본을 한 칸에 넣으면 나머지 칸과의 연결이 끊어진다. 위키는 회의록을 주제별로 쪼개 각 칸의 페이지에 나눠 담을 수 있다.

**PARA 상태는 시간이 지나면 바뀐다.** 프로젝트가 끝나면 Archives로 옮겨야 하는데, 원본을 옮기면 위키에 적어 둔 출처 경로가 모두 깨진다. 정리본은 옮겨도 되지만 증거는 제자리에 있어야 한다.

**두 폴더의 역할이 다르다.** 원본 폴더는 "무엇이 언제 들어왔나"를 기록하는 증거 보관함이고, PARA는 "지금 무엇을 실행하나"를 정하는 행동 분류다.

원본은 출처 종류별 폴더에 날짜를 앞에 붙인 파일명으로 쌓는다.

```text
raw/
├── meetings/   2026-10-20_주간회의록.md
├── data/       2026-09_매출집계.csv
├── mail/       2026-10-27_거래처_변경공지.md
└── web/        2026-10-25_핸드워시_경쟁사/
```

- 원본이 어느 PARA 칸과 관련되는지는 위키 페이지의 출처 링크가 알려 준다. 반대 방향은 옵시디언의 백링크로 확인한다.
- 원본이 너무 많아지면 해마다 `raw/_2025/`처럼 연도 폴더로 묶는다. 경로 규칙이 일정하므로 Claude가 위키의 출처 링크를 함께 고칠 수 있다.

```text
raw 폴더를 meetings, data, mail, web 네 폴더로 나누고 파일명 앞에 날짜를 붙여 정리해 줘.
옮기기 전에 바뀔 경로 목록을 먼저 보여 주고, 내가 승인하면 옮긴 뒤
위키의 출처 링크를 새 경로로 모두 고치고 log.md에 기록해 줘.
```

### 3.3 모닝리빙 예시로 매핑하기

| PARA 칸 | 모닝리빙 위키 페이지 | 판단 기준 |
|---|---|---|
| 1_Projects | 11월 프로모션, 핸드워시 경쟁사 대응 | 끝나는 날짜와 목표가 있다 |
| 2_Areas | 거래처별 페이지, 월간 매출 집계, 주간 보고 | 담당하는 동안 계속 이어진다 |
| 3_Resources | 회사 개요, 용어와 상태 구분, 경쟁사 조사 자료 | 여러 일에서 참고한다 |
| 4_Archives | 끝난 프로모션, 계약이 끝난 거래처 | 더 이상 실행하지 않는다 |

### 3.4 결합해서 얻는 효과

1. **분류를 AI가 맡는다.** 인제스트할 때 새 정보를 어느 칸에 넣을지 Claude가 판단하고, 애매할 때만 사람에게 묻는다.
2. **수명주기를 관리할 수 있다.** 프로젝트가 끝나면 Claude가 페이지를 `4_Archives`로 옮긴다. 점검할 때는 기한이 지났는데 `1_Projects`에 남아 있는 페이지를 찾아낸다.
3. **질의 범위가 좁아진다.** 주간 보고는 `1_Projects`와 `2_Areas`만, 경쟁 분석은 `3_Resources`를 중심으로 읽게 하면 답이 정확해지고 크레딧도 줄어든다.

### 3.5 CLAUDE.md에 추가할 규칙

```markdown
## PARA 분류 (wiki/ 안에만 적용)
- 기한과 목표가 있는 일은 1_Projects, 계속 맡는 책임은 2_Areas,
  참고 지식은 3_Resources, 끝났거나 쓰지 않는 것은 4_Archives에 둔다.
- 분류가 애매하면 나에게 묻는다.
- 한 페이지는 한 칸에만 둔다. 다른 칸과의 관계는 [[링크]]로 표현한다.
- 프로젝트가 끝나면 4_Archives로 옮기고 log.md에 날짜와 이유를 남긴다.
- raw/ 의 원본은 PARA로 옮기지 않는다.
```

### 3.6 PARA 실습 프롬프트

**기존 위키를 PARA로 재배치하기**

```text
wiki/ 안의 페이지를 PARA 네 칸(1_Projects, 2_Areas, 3_Resources, 4_Archives)으로 재배치하려고 해.
바로 옮기지 말고 페이지별로 어느 칸에 둘지와 그 이유를 표로 먼저 보여 줘.
내가 승인하면 옮기고, 깨지는 링크가 없도록 고친 뒤 index.md를 새 구조에 맞게 다시 써 줘.
위 PARA 규칙을 CLAUDE.md에도 추가해 줘.
```

**프로젝트 종료 처리**

```text
11월 프로모션이 끝났어. 결과를 프로젝트 페이지에 정리하고,
다음 프로모션에 쓸 교훈은 3_Resources의 "프로모션 운영 노하우" 페이지로 옮겨 줘.
그다음 프로젝트 페이지를 4_Archives로 옮기고 log.md에 기록해 줘.
```

**PARA 점검**

```text
PARA 구조를 점검해 줘.
- 기한이 지났는데 1_Projects에 남아 있는 페이지
- 6개월 동안 아무 페이지도 링크하지 않은 3_Resources 페이지
- 두 칸에 비슷한 내용이 중복된 페이지
를 표로 보여 주고, 옮기거나 합칠 방법을 제안해 줘. 실제 수정은 내가 승인한 뒤에 해.
```

> [!tip] PARA를 더 단순하게 쓰고 싶다면
> 칸을 셋으로 줄여 실행(Projects), 운영(Areas), 발견(Resources)으로 나누고, 끝난 것은 각 칸 안의 `_archive/` 폴더로 보내도 된다. 원리는 같다. 위키 안을 실행 가능성으로 나누고, 원본은 건드리지 않는다.

## 4. 왜 옵시디언인가 — 여섯 가지 이유

1. **원조 사례**다. LLM 위키 방식이 처음 소개될 때 옵시디언을 보는 창으로 썼다.
2. **오프라인**에서도 열린다. 파일이 내 컴퓨터 폴더에 그대로 있기 때문이다.
3. **사람이 읽기 좋은 형태**로 저장한다. 마크다운(.md) 문서라 메모장으로도 열리고, AI가 무엇을 썼는지 바로 점검할 수 있다.
4. **어떤 AI와도 연결**된다. 결국 평범한 폴더와 텍스트 파일이므로 Claude, ChatGPT, Codex 어느 쪽이든 읽을 수 있다.
5. **무료**다.
6. **평생 자산**이 된다. 특정 서비스가 사라져도 폴더는 내 컴퓨터에 남는다.

> [!tip] 함께 알면 좋은 옵시디언 기능
> - `[[페이지명]]` 링크: 페이지끼리 연결한다. AI에게도 이 형식으로 링크를 걸라고 규칙에 적는다.
> - 그래프 뷰(Ctrl/Cmd + G): 쌓인 페이지가 어떻게 연결되어 있는지 점과 선으로 보여 준다.
> - 백링크(backlinks): 지금 페이지를 참조하는 다른 페이지 목록을 보여 준다.

## 5. 기본 실습 — 영상 재현 (모닝리빙 영업관리팀)

**시나리오**: 생활용품 브랜드 "모닝리빙" 영업관리팀의 김영업 주임이 되어 세컨드 브레인을 만든다.

### Step 1. 옵시디언 설치와 볼트 생성

1. 옵시디언 **공식 홈페이지**(obsidian.md)인지 확인하고, 내 운영체제에 맞는 설치 파일을 받는다.
2. 처음 실행하면 나오는 "보관함 생성(Create new vault)"을 누른다.
3. 보관함 이름에 `MorningLiving_SecondBrain`을 입력하고, 위치는 예제 파일을 내려받은 폴더로 지정한다.
4. 가운데에 메모장 같은 편집 화면이, 오른쪽에 그래프 뷰가 보이면 성공이다.

### Step 2. Claude에 같은 폴더 연결

- **Claude 데스크톱 앱**: 왼쪽의 프로젝트(폴더) 추가 버튼으로 방금 만든 볼트 폴더를 선택한다.
- **Claude Code**: 터미널에서 볼트 폴더로 이동한 뒤 `claude`를 실행한다.

> [!important] 핵심
> 옵시디언과 Claude가 **같은 폴더**를 바라봐야 한다. 옵시디언은 사람이 보는 창이고, Claude는 그 폴더에 파일을 쓰는 손이다.

### Step 2-1. 실습 원본 자료를 Claude에게 만들게 하기

영상은 예제 파일을 따로 배포하지만, 이 실습에서는 Claude가 가상 원본 자료를 직접 만든다. 수강생은 아래 프롬프트를 붙여 넣고 결과만 확인한다.

```text
실습용 가상 원본 자료를 만들어 줘. 실제 회사·인물 이름은 쓰지 마.

[설정]
- 회사: 생활용품 브랜드 모닝리빙 (주방세제, 핸드워시, 섬유유연제)
- 나: 영업관리팀 김영업 주임, 상사는 박팀장
- 거래처: 대형마트 3곳, 온라인몰 2곳 (가상 이름)

[만들 위치]
_sample_data/1_처음 넣을 자료/ 에 아래 파일을 만들어 줘.
- 회사소개.md : 제품군, 조직, 영업관리팀 역할
- 거래처_리스트.csv : 거래처명, 채널, 담당자, 월 매출, 계약 상태
- 용어와_상태구분.md : 사내 용어, 발주·납품·정산 상태 정의
- 2026-10-13_주간회의록.md, 2026-10-20_주간회의록.md
- 9월_매출집계.csv : 거래처별·제품별 매출
- 프로모션_일정.md : 11월 행사 계획

_sample_data/2_업무 진척 자료/ 에 아래 파일을 만들어 줘.
- 2026-10-27_주간회의록.md : 1차 회의록에서 정한 프로모션 일정 하나를 번복하는 내용 포함
- 거래처_변경공지.md : 거래처 한 곳의 담당자와 계약 조건 변경
- 10월_매출집계.csv

[조건]
- 1차 자료 안에 서로 모순되는 내용 하나를 일부러 섞어 줘. 나중에 점검 실습에 쓴다.
- _sample_data 폴더는 실습 준비물이니, 나중에 위키 작업을 할 때는 읽지 마.
다 만들면 파일 목록과 각 파일의 핵심 내용을 한 줄씩 알려 줘.
```

> [!check] 확인 포인트
> 옵시디언 왼쪽 파일 목록에 `_sample_data` 폴더와 두 하위 폴더가 보이는가?

### Step 3. 세팅 계획 세우기 (프롬프트 2-1)

```text
이 폴더를 내 업무용 "세컨드 브레인"으로 만들려고 해.
카파시의 LLM Wiki 방식을 따른다.
- raw/ : 원본 자료. 너는 읽기만 하고 절대 수정하지 않는다.
- wiki/ : 네가 원본을 정리해 쓰는 마크다운 페이지. 페이지끼리 [[링크]]로 연결한다.
- CLAUDE.md : 폴더 구조, 페이지 양식, 링크 규칙, 인제스트 절차를 적는 규칙 파일.

바로 만들지 말고 먼저 세팅 계획을 세워 줘.
내 직무에 맞는 폴더 구조와 페이지 목록을 제안하고,
시작하기 전에 나에게 확인할 질문을 해 줘.
```

### Step 4. Claude의 질문에 답하기

Claude는 계획과 함께 질문을 던진다. 처음 한 번은 나를 소개해야 한다.

```text
1. 실습 원본 자료는 _sample_data 폴더에 있어. 폴더 구조를 만든 뒤 내가 요청하면 raw로 옮겨 줘.
2. 회사와 직무는 다음과 같아.
   - 회사: 생활용품 브랜드 모닝리빙 (주방세제, 핸드워시, 섬유유연제)
   - 소속: 영업관리팀 주임 김영업
   - 담당: 대형마트·온라인몰 거래처 관리, 월간 매출 집계, 프로모션 일정 조율, 주간 보고
   - 보고 대상: 박팀장, 주간 보고는 슬랙으로 짧게
이대로 계획을 실행해 줘.
```

### Step 5. 원본 넣고 인제스트

원본을 넣는 일도 Claude에게 시킨다. 하위 폴더에 하나하나 나눠 넣을 필요는 없다.

```text
_sample_data/1_처음 넣을 자료/ 의 파일을 모두 raw 폴더로 복사하고 인제스트해 줘.
```

> [!note] 실제 업무로 넘어갈 때
> 내 업무 파일은 탐색기(Finder)에서 `raw/` 폴더에 직접 붙여 넣고 "raw에 새 파일을 넣었어. 인제스트해 줘."라고만 하면 된다.

> [!example] 결과
> `wiki/` 아래에 개요, 회사 소개, 용어와 상태 구분, 거래처, 업무 프로세스 페이지가 생기고 서로 링크로 연결된다.

### Step 6. 첫 테스트 — 주간 보고

```text
팀장님께 슬랙 메시지로 보낼 짧은 주간 보고를 써 줘.
완료한 업무와 진행 중인 업무를 나눠 주고, 근거가 된 위키 페이지를 끝에 적어 줘.
```

### Step 7. 두 번째 테스트 — 웹 조사 후 위키에 저장

```text
우리 제품 중 핸드워시의 경쟁 브랜드 세 곳을 공식 사이트와 공식 판매처 위주로 조사해서
영업관리 담당자 관점의 인사이트를 제안해 줘.
수집한 원문은 raw/web/오늘날짜_핸드워시_경쟁사/ 에 저장하고,
정리한 내용은 위키에 새 페이지로 만들어 관련 페이지와 링크로 연결해 줘.
```

> [!check] 확인 포인트
> 수집 원문이 `raw/web/`에 날짜별로 남아 있는가? 위키의 새 페이지가 그 원문을 출처로 가리키는가? 그래야 나중에 "이 결론이 어디서 나왔는지" 추적할 수 있다.

### Step 8. 업무 진척 반영 — 추가 자료

```text
_sample_data/2_업무 진척 자료/ 의 파일을 모두 raw 폴더로 복사하고 인제스트해 줘.
기존 위키에서 바뀐 부분을 알려 주고, 다음 주 할 일 목록을 정리해 줘.
```

### Step 9. 결정이 번복될 때 — 변경 이력 관리

```text
앞으로 자료끼리 내용이 충돌하면 이렇게 처리해 줘.
- 더 최근 자료를 현재 기준으로 삼는다.
- 위키 본문은 새 내용으로 고치고, 페이지 맨 아래 "변경 이력"에
  날짜, 이전 내용, 바뀐 이유, 근거 원본 파일명을 남긴다.
- 옛 내용을 지우기만 하지 말고 무엇이 바뀌었는지 나에게 요약해 준다.
이 규칙을 CLAUDE.md에 추가해 줘.
```

### Step 10. 그래프 뷰로 연결 확인

옵시디언에서 **Ctrl + G**(Mac은 Cmd + G)를 눌러 페이지들이 어떻게 연결되어 있는지 확인한다. 외톨이 점(링크 없는 페이지)이 많으면 점검(lint)을 요청한다.

## 6. 직무별 실습예제

모든 예제는 같은 흐름을 따른다.

> **① 예제 원본 만들기 → ② 세팅 계획 → ③ 인제스트 → ④ 질의 테스트 2개 → ⑤ 업데이트·번복 테스트 → ⑥ 확인**

> [!tip] 예제 원본도 Claude에게 만들게 한다
> 실습용 원본 파일이 없으면 아래 프롬프트로 가상 자료부터 만든다. 수강생은 프롬프트를 붙여 넣고 결과만 확인하면 된다.
>
> ```text
> 실습용 가상 원본 자료를 만들어 줘. 실제 회사·인물 이름은 쓰지 마.
> 직무: (아래 예제의 직무)
> raw/ 폴더에 아래 목록대로 파일을 만들고, 일부러 서로 모순되는 내용 하나와
> 날짜가 지난 정보 하나를 섞어 줘. 나중에 점검 실습에 쓸 거야.
> 처음 넣을 자료는 raw_batch1/, 나중에 넣을 진척 자료는 raw_batch2/ 에 나눠 담아 줘.
> ```

### 예제 1. 마케팅 — 브랜드 톤 일관성 유지

**시나리오**: 식품 스타트업 "그린테이블" 콘텐츠 마케터 이마케.

| 구분 | 원본 자료(raw) |
|---|---|
| 1차 | 브랜드 가이드라인, 금지 표현 목록, 지난 분기 SNS 게시물 30개와 반응 수치, 타깃 페르소나 정리 |
| 2차 | 신제품 출시 기획안, 리브랜딩으로 바뀐 슬로건 |

**질의 테스트**

```text
1. 신제품 그래놀라 출시를 알리는 인스타그램 캡션 3안을 써 줘.
   브랜드 톤 가이드와 금지 표현을 지키고, 어느 위키 페이지를 따랐는지 표시해 줘.
2. 지난 분기 게시물 중 반응이 좋았던 유형 세 가지와 그 이유를 위키에 "콘텐츠 성과 패턴" 페이지로 만들어 줘.
```

**번복 테스트**: 2차 자료의 새 슬로건을 넣은 뒤 "이전 슬로건이 남아 있는 위키 페이지를 모두 찾아 고쳐 줘"라고 요청한다.

**확인**: 캡션에 금지 표현이 섞이지 않았는가? 옛 슬로건이 위키에서 모두 사라지고 변경 이력에 남았는가?

### 예제 2. 인사·총무 — 사내 규정 문의 응대

**시나리오**: 중견 제조사 인사팀 최인사 대리.

| 구분 | 원본 자료(raw) |
|---|---|
| 1차 | 취업규칙, 연차·휴가 규정, 복리후생 안내문, 출장비 기준표, 자주 묻는 질문 메일 20건 |
| 2차 | 올해 개정된 출장비 기준(숙박비 상한 인상), 신규 육아 지원 제도 공지 |

**질의 테스트**

```text
1. "입사 8개월 차인데 연차가 며칠인가요?"라는 직원 문의에 답하는 메일을 써 줘.
   근거 조항을 위키 페이지와 원본 파일명으로 함께 적어 줘.
2. 신입사원 첫 주에 꼭 알아야 할 규정 10가지를 위키에 "온보딩 체크리스트" 페이지로 만들어 줘.
```

**번복 테스트**: 개정 출장비 기준을 넣은 뒤 "출장비 관련 답변 템플릿 중 옛 기준을 쓰는 것을 찾아 고쳐 줘"라고 요청한다.

**확인**: 답변마다 근거 조항이 붙는가? 규정에 없는 내용을 지어내지 않았는가? (위키에 없는 내용은 "규정에서 확인되지 않음"이라고 답하도록 `CLAUDE.md`에 적어 둔다.)

### 예제 3. 개발 — 사내 기술 규칙과 장애 이력

**시나리오**: 쇼핑몰 백엔드 개발자 정개발.

|---|---|
| 1차 | 코드 컨벤션 문서, 사내 API 명세, 아키텍처 결정 기록(ADR) 5건, 지난 장애 회고(postmortem) 3건 |
| 2차 | 결제 모듈을 새 PG사로 바꾸기로 한 ADR, 신규 장애 회고 1건 |

**질의 테스트**

```text
1. 주문 취소 API를 새로 만들 때 지켜야 할 사내 규칙을 컨벤션과 API 명세 기준으로 정리해 줘.
```

**번복 테스트**: 결제 모듈 변경 ADR을 넣은 뒤 "옛 PG사를 전제로 한 위키 내용을 찾아 고치고, 변경 이력에 ADR 번호를 남겨 줘"라고 요청한다.

**확인**: 체크리스트 항목마다 어느 회고에서 나왔는지 링크가 걸렸는가?

**시나리오**: 구청 환경과 주무관 윤민원.

| 구분 | 원본 자료(raw) |

## 7. 공통 응용 실습

### 7.1 점검(lint) — 위키 건강검진

```text
위키 전체를 점검해 줘.
- 서로 모순되는 내용
- 근거 원본이 없는 주장
- 링크가 하나도 없는 외톨이 페이지
- 90일 넘게 갱신되지 않은 페이지
를 찾아 표로 보고하고, 고칠 방법을 제안해 줘. 실제 수정은 내가 승인한 뒤에 해.
```

### 7.2 대화 결과물 회수

```text
오늘 이 대화에서 만든 결과물 중 다시 쓸 만한 것(결정, 표, 템플릿)을
위키의 알맞은 페이지에 반영하고, log.md에 오늘 날짜로 기록해 줘.
```

### 7.3 주간 회고

```text
이번 주 raw에 들어온 자료와 log.md를 바탕으로 주간 회고를 써 줘.
잘된 일, 막힌 일, 다음 주 우선순위 세 가지로 나눠 주고 위키 "주간 회고" 폴더에 저장해 줘.
```

### 7.4 규칙 파일을 다듬는 프롬프트

```text
지금까지 작업하면서 반복해서 내가 고쳐 달라고 한 것이 있으면
CLAUDE.md의 규칙으로 옮겨 적어 줘. 바꾼 규칙은 나에게 먼저 보여 줘.
```

## 8. CLAUDE.md 기본 템플릿

```markdown
# 세컨드 브레인 운영 규칙

## 폴더
- raw/ : 원본. 읽기만 하고 절대 수정·삭제하지 않는다. PARA로 나누지 않고 meetings, data, mail, web 폴더에 날짜를 붙여 쌓는다.
- raw/web/날짜_주제/ : 웹에서 수집한 원문을 저장한다.
- wiki/ : 정리본. 페이지마다 아래 양식을 따른다.
- wiki/log.md : 인제스트·수정할 때마다 날짜와 내용을 한 줄씩 남긴다.

## 페이지 양식
- 맨 위: 한 줄 요약
- 본문: 사실은 원본 파일명을 출처로 단다. 원문에 없는 해석은 "해석:"으로 시작한다.
- 맨 아래: 변경 이력(날짜, 이전 내용, 바뀐 이유, 근거 원본)

## 링크
- 관련 페이지는 [[페이지명]]으로 연결한다.
- 새 페이지를 만들면 wiki/index.md 목차에 추가한다.

## 충돌과 번복
- 더 최근 자료를 현재 기준으로 삼고, 바뀐 내용을 사용자에게 요약해 보고한다.

## 금지
- 개인정보(주민번호, 연락처, 계좌 등)는 위키에 옮기지 않는다.
- 원본에 없는 숫자나 사실을 지어내지 않는다. 모르면 "원본에서 확인되지 않음"이라고 쓴다.
```

## 9. 운영 시 주의할 점

| 주의할 점 | 이유와 대처 |
|---|---|
| 원본은 고치지 않는다 | 원본이 바뀌면 위키의 근거를 추적할 수 없다. 규칙 파일에 "raw는 읽기 전용"을 반드시 적는다. |
| 사내 기밀은 회사 보안 정책을 먼저 확인한다 | 폴더는 내 컴퓨터에 있어도, 작업할 때 내용이 AI 서비스로 전송된다. 반출이 금지된 자료는 넣지 않는다. |
| 위키를 맹신하지 않는다 | AI가 요약하다 틀릴 수 있다. 중요한 숫자는 원본과 대조하고, 주기적으로 점검(lint)한다. |
| 처음부터 크게 만들지 않는다 | 자료 5~10개로 시작해 질의가 잘 되는지 확인한 뒤 늘린다. |
| 백업 | 폴더째 클라우드 드라이브나 git으로 백업하면 실수로 지워도 되살릴 수 있다. |
| 크레딧 | 인제스트는 한 번에 몰아서 하고, 질의는 위키를 근거로 하게 하면 원본을 매번 다시 읽지 않아 소모가 줄어든다. |

## 11. 자주 묻는 질문

**Q. 프로젝트 지침이나 메모리와 같이 써도 되나?**
된다. 지침에는 "이 폴더의 `CLAUDE.md`와 `wiki/index.md`를 먼저 읽어라" 한 줄만 두고, 세부 내용은 위키에 둔다.

**Q. ChatGPT나 다른 AI로도 되나?**
된다. 결국 폴더와 마크다운 파일이므로 폴더를 읽고 쓸 수 있는 도구라면 같은 구조를 그대로 쓸 수 있다.

**Q. 위키 페이지가 수백 개로 늘면 어떻게 하나?**
`index.md`를 주제별 하위 목차로 나누고, 질의할 때 "먼저 index에서 관련 페이지를 고른 뒤 그 페이지만 읽어라"라고 규칙에 적는다. 그래도 커지면 검색 도구(RAG)를 붙이는 단계로 넘어간다.

**Q. 엑셀이나 PDF도 넣을 수 있나?**
넣을 수 있다. 인제스트할 때 Claude가 내용을 읽어 위키에는 마크다운 요약과 핵심 표로 옮긴다. 원본 파일은 `raw/`에 그대로 둔다.
